# Конструктор историй для WordPress

## Решение

Истории могут быть разной длины и с разным сценарием. Унифицировать нужно не число секций, а библиотеку секций, их поля и правила отображения.

Для редактора лучше сделать одноуровневый упорядочиваемый конструктор без свободной HTML-разметки и глубокой вложенности. Внутри отдельных блоков допустимы повторяемые элементы: карточки, шаги, показатели и пункты результата.

## Типы блоков

1. `hero` — обязательный заголовок H1, вводный текст и главное медиа.
2. `text` — текстовая глава без медиа.
3. `text_media` — текст и фото или видео слева/справа.
4. `quote` — прямая речь, при необходимости с аудио.
5. `media` — отдельное видео, аудио или фото с подписью.
6. `before_after` — пара или галерея фотографий до/после.
7. `metrics` — показатели, результаты обследований и обязательное пояснение контекста.
8. `cards` — наблюдения, маркеры или этапы в карточках.
9. `checklist` — список изменений или результатов.
10. `timeline` — последовательность этапов работы.
11. `statement` — крупная смысловая цитата или поворотный момент.
12. `expert_comment` — комментарий Светланы.
13. `recognition` — «эта история может быть близка вам, если…».
14. `cta` — обязательный финальный призыв и дисклеймер.

Подпись, источник, дисклеймер и предупреждение о персональных данных должны быть полями соответствующего блока, а не отдельными декоративными секциями.

## Общие поля блока

- стабильный идентификатор и якорь;
- служебное название для списка в админке;
- надзаголовок, заголовок и вводный текст;
- тема только из списка `canvas`, `surface`, `dark`;
- вертикальный ритм только `compact` или `regular`;
- видимость блока;
- медиа через ID вложения, alt, подпись, фокусную точку и вариант кадрирования;
- флаг приватности для лица или персональных данных;
- повторяемые элементы с ограничением количества там, где это нужно.

Произвольные CSS-классы, цвета, размеры текста и HTML редактору не выдаются. Это сохранит дизайн при добавлении новых историй.

## Хранение в WordPress

- отдельный CPT `story`;
- таксономия `story_problem` для фильтрации по запросу;
- обычные поля WordPress без ACF;
- порядок блоков хранится в одном версионированном и санитизированном JSON-meta, например `_story_layout_v1`;
- связанные изображения и видео хранятся как attachment ID, а не как URL;
- PHP-реестр сопоставляет `type` блока с одним шаблоном и схемой допустимых полей;
- при изменении схемы добавляется миграция `v1 → v2`, старые записи не переписываются вручную.

Глубокий «подконструктор» не нужен: он быстро создаёт непредсказуемые комбинации. Достаточно одного уровня блоков и повторяемых строк внутри `cards`, `metrics`, `checklist` и `timeline`.

## Ограничения, которые проверяет админка

- ровно один `hero`, он первый;
- ровно один `cta`, он последний;
- H1 заполняется отдельно, осмысленно описывает историю и визуально крупнее любого H2;
- заголовки блоков идут по иерархии H2 → H3 без пропусков;
- основной текст не шире 68–72 символов в строке;
- размер любого отображаемого текста не меньше 12 px;
- у каждого содержательного изображения есть alt и фокусная точка;
- подряд допускается не больше одного крупного тёмного блока;
- медицинские показатели требуют пояснения и источника;
- блок нельзя опубликовать с недостающим обязательным медиа или видимыми персональными данными.

## Миграция текущих историй

Сначала создаётся реестр компонентов и схема полей. Затем текущие TypeScript-данные переводятся в JSON-фикстуры той же формы. После визуального сравнения фикстуры импортируются в CPT, а frontend начинает получать тот же объект из WordPress REST API или серверного PHP-рендера. Такой порядок позволяет не менять дизайн одновременно с переносом контента.
